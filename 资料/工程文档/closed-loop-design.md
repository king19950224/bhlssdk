# 监测业务闭环设计（closed-loop）

状态：P0 已实施（2026-08-19）· 本文档为闭环全景蓝图与分期计划

## 0. 为什么要闭环

2026-08-19 上午的真机事件把断点全部暴露了一遍：

- CH8 报"目标的 4776%"严重告警，**告警只报数不报因**，人工排查半小时才定位到"标定时基线锁错回波"；
- 5 颗螺栓的目标预紧力是建档时的占位值（100/150 kN），与实际拧紧扭矩（200 N·m ≈ 50 kN）对不上，
  **配置错误制造假告警**（153.6% "偏高"）；
- CH8 信号质量差（SNR 8 dB）却能直接进标定流程，**坏信号标出坏基线**没有任何拦截；
- 告警恢复后没人记录"这条告警最终是什么"，**误报没有留下可统计的痕迹**，
  下次还会用同样的方式再错一遍。

闭环的定义：**每个异常都有诊断，每个处置都有归因，每个配置都可追溯到物理动作，
每类误报都反哺预防规则。** 系统不只是"显示状态"，而是回答"下一步做什么"。

## 1. 全生命周期七阶段与守卫

```
接入 → 建档 → 标定 → 监测 → 告警 → 处置 → 复核
 ↑                                            │
 └────────────── 归因反哺预防 ←───────────────┘
```

| 阶段 | 入口 | 守卫（防错设计） | 状态 |
|---|---|---|---|
| A 接入 | 插探头自动识别 | 探头扫描判定（信号质量分级）、墓碑通道防复活 | 已有 |
| B 建档 | 自动建档（占位档）/ 人工建档 | 两级档案（占位/资产）；**扭矩→目标换算联动（P0 新增）** | 已有+P0 |
| C 标定 | 标定向导 | 置零稳定性守卫（±3ns）、在役/实验室场景硬拦截、**SNR<12dB 前置警告（P0 新增）** | 已有+P0 |
| D 监测 | 采集热路径 | 温补、GB 范围门、**前端可信域兜底（>300%/<5% 判超范围）** | 已有 |
| E 告警 | 阈值评估器 | 连击去抖、自动恢复、抑制白名单 | 已有 |
| F 处置 | 告警中心 | **五项规则诊断（P0 新增）**、**结构化归因闭合（P0 新增）** | P0 |
| G 复核 | KPI / 到期清单 | 标定到期提醒、**归因分布与误报率（P0 新增）** | 已有+P0 |

## 2. P0 已实施（2026-08-19）

### 2.1 告警诊断（GET /api/alarms/{id}/diagnosis）

五项规则检查，按优先级给根因结论——就是 CH8 那次人工排查的固化：

| 检查 | 证据 | 不通过的含义 |
|---|---|---|
| 探头链路 | 90 秒内测量条数 | 链路断（查接线/供电） |
| 信号质量 | 最新波形 SNR ≥ 12 dB | 耦合差（重新耦合） |
| 基线合理性 | 有效比值 ∈ [5%, 300%] 且 声时漂移 ≤ 1000ns | 基线锁错回波 / 规格错（重标+锚定） |
| 范围门拒算率 | 最近 10 分钟拒算 ≤ 30% | 读数摆动（信号或基线问题） |
| 同组共模 | 同组其他螺栓中位比值正常 | 共模=工况/配置问题；独立=本颗问题 |

结论五值：`link_down / baseline_suspect / sensor_issue / common_mode / likely_real`，
每个结论带具体处置建议与入口指引。

### 2.2 结构化归因闭合（0035 迁移）

`alarms.resolution`（CHECK 白名单）：

- 真实告警：`real_loosening` / `real_overload`
- 误报根因：`baseline_error` / `sensor_issue` / `config_error` / `external_operation` / `other`

闭合对话框强制选归因+说明；KPI 页新增"处置归因分布"卡（已归因数、误报占比、逐项分布）。
**误报占比高 → 先治根因（基线/耦合/配置），不许调松阈值**——这是报警合理化评审的铁律。

### 2.3 扭矩→目标联动（建档对话框 + 螺栓设置）

`F = T/(K·d)`，K 按润滑状态选（干燥 0.20 / 轻润滑 0.15 / 润滑 0.13）。
填实际拧紧扭矩一键换算目标与下限（70%），目标值从此可追溯到物理动作。

### 2.4 标定向导 SNR 前置守卫

进向导先查最新波形 SNR，< 12 dB 亮警告：先治耦合再标定。
（置零的 ±3ns 稳定性守卫、在役场景"不许拧动"硬拦截此前已有。）

## 3. P1 计划（一周内）

1. **信号健康巡检**：SNR 趋势退化检测（7 天滑窗斜率），退化过快发提示性告警
   "建议检查耦合"——耦合剂干涸是缓慢过程，等信号丢失才发现就晚了。
2. **诊断入口前移**：总览/资产页的异常状态点击直达诊断（现在在告警中心行上）。
3. **归因驱动的规则建议**：某点位 `config_error` 归因 ≥2 次 → 提示核对该组目标配置。

## 4. P2 计划（发布后迭代）

1. 批次管理：K_L 按"螺栓批次"归档复用（现在用同组同规格中位数近似）。
2. 处置工单：告警 → 生成检修工单 → 完成回执自动闭合并归因（对接运维系统）。
3. 归因统计进月报：误报率趋势、根因帕累托图入验收/运维报告。

## 5. 设计纪律（复盘沉淀）

1. **告警必须能回答"下一步做什么"**——只报数字的告警是把排查成本转嫁给现场。
2. **配置必须可追溯到物理动作**——"目标 50 kN"必须能回答"哪来的"（200 N·m × K=0.20）。
3. **误报是数据，不是噪音**——归因分布指向系统性缺陷；调松阈值掩盖问题是被禁止的处置方式。
4. **守卫放在入口，不放在事后**——坏信号进不了标定，比标废之后再诊断便宜一百倍。
