# SDK 1.6 能力选型与软件设计

写作日期：2026-08-12。前置文档：`sdk-1.6-upgrade-assessment.md`（换版影响评估）、`sdk-1.6-upgrade-plan.md`（换源执行，已完成）。

本文回答的是换源之后的问题：**1.6 提供的这堆能力，我们的软件哪些该用、哪些不该用、什么时候用**。依据三份材料：厂家《FxSDK1.6 多通道监测版开发指南 V2.0》（`bhls1.6/sdk16/`，下称"指南"）、厂家《iFast 多通道监测三种测量算法说明 2.0》（下称"算法说明"）、1.6 全量源码精读。

---

## 0. 结论一页

| # | 能力 | 结论 | 一句话理由 |
|---|---|---|---|
| 1 | 阈值法（MeasMode=2） | **保持生产主力** | 标定体系绑定其上；厂家定位"易人工校核"，正合安全关键场景 |
| 2 | 自动法（MeasMode=0，Beta） | **实验室试点，验证后放产** | 厂家"长期监测首选"；锚点持久化链路本周已建好，就差数值验证 |
| 3 | 动态特征法（MeasMode=1） | **不入生产** | 包络漂移"不报错地出错"，与安全监测的可追责性冲突 |
| 4 | FxServer 设备主动接入 | **挂起，触发条件明确** | 现场是固定 IP 串口服务器，FxClient 够用；4G/NAT 需求出现再做 |
| 5 | 温度 Tau 平滑 | **保持 Direct（已定）** | 历史口径连续性优先；通道级 TempTauSeconds 留作个案手段 |
| 6 | 信号质量分开监控 | **近期补强（本文唯一的新增开发建议）** | 厂家强要求；我们有底子，缺"有帧但劣化"的检测 |
| 7 | AGC 自动增益 | **要用再接，只进调试工位** | 验收/调参有用；无人值守自动跑有跨周期风险 |
| 8 | SDK DeltaTof / CalcUltraResult | **继续不用** | 预紧力链必须走自家标定体系，不能依赖 SDK 内嵌换算 |
| 9 | Model=5 / 多终端 LoRa / 双波横波 | **挂起** | 无对应硬件与场景；双波值得向厂家求证能力 |

## 1. 先把 1.6 的本质变化说清楚

1.4 的 SDK 是一根"协议管子"：字节进、结果出，无状态。1.6 变成了一个**带算法状态的测量引擎**，三个证据：

1. **自动法有状态化**——`EnvelopeTrackingContext` 扫波期最多存 5 组锚点，F0/Z0 从声时中位数帧成对选取、T0 取有效周期中位数；置零后靠 `RefEnvTime`/`RefPeriodNs`/`LEchoWave` 跨重启锁周期。指南 §5.5 明说这是"应用需要持久化并回灌的算法上下文，不等同于设备寄存器"——**状态管理责任在我们**，这正是本周 0031 迁移 + 回灌链路做的事。
2. **温度从透传变成管线**——RawTemp（原始）→ 范围保护（−40~120，超限用会话代表温度顶）→ Tau 平滑 → SpTemp（业务）。选择权（Tau 策略、通道级系数、独立温度通道 UseTempChannel）全部交给应用。
3. **会话健康从写死变成可配**——TcpSessionOptions（心跳/接收超时）、FxServer 的 Identify/ReceiveIdle/DecodeIdle 三级超时、SessionTraffic 流量观测。

这意味着选型不再只是"连上取数"，而是要对**算法状态的生命周期**负责：谁产生（置零）、谁保存（库）、谁回灌（启动 provisioning）、谁失效（换螺栓/改增益）。我们软件的架构恰好是按这个责任划分建的（SDK 会话状态 ⇄ channels 表 ⇄ SessionContext），对位良好。

## 2. 测量模式怎么选（核心决策）

### 2.1 厂家的口径（算法说明全文要点）

| | 自动法（Beta） | 动态特征法 | 阈值法 |
|---|---|---|---|
| 定位 | 包络粗定位 + 同相上升沿过零（F0/Z0/T0 预测） | 包络前沿过 30% 动态阈值点 | 过阈值后找正向上升沿过零 |
| 精度 | 相位级，散点小 | **周期级**，短期波动大 | 阈值有效区内相位级 |
| 长期容忍 | 回波跨周期移动、幅值一定变化 | 幅值等比变化，但包络形状不能变 | 幅值/极性/增益/耦合都要稳 |
| 失败方式 | 无效帧（可检测）；强干扰时可能选错主回波（**有数值的错**） | 包络变形 → **缓慢漂移不报错** | 跌破阈值 → 无数据；误命中 → 跳阶 |
| 厂家定位 | **长期监测首选** | 趋势监测备选 | 条件明确、易人工校核 |

### 2.2 我们的决策

**生产存量通道：保持阈值法。** 三个理由：

1. 全部标定系数（`k_l`/`c_0`）是对着阈值法的声时提取拟合的，1.6 的阈值法与 1.4 实质等价（评估 §4.1，次奈秒级），**不换模式 = 不重标定**；
2. 商用安全场景要的是"错了能查"：阈值线画在波形图上人人能复核，自动法的 F0/Z0/T0 预测解释成本高；
3. 自动法官方标注 **Beta**（评估 §10 求证问题 #5 厂家还没回）。

**阈值配置规则**（写给现场，落 `calibration-field-guide.md`）：

- 阈值必须落在"噪声峰值之外、最低幅值工况的目标回波之内"（指南 §阈值法工作过程第 2 步）。验收时记录常温峰值，阈值取噪声峰值 ×2 与目标峰值 ×0.5 之间靠下的位置；
- `Threshold=0`（正峰 60% 相对阈值）适合幅值波动大但波形干净的通道——相对阈值随幅值等比缩放不跳周期（评估 §4.4 论证过），但**不适合正峰很弱或负峰为主的波形**（算法说明原文）；
- 负阈值 = 找下降越阈后仍取正向过零，波形负峰为主时用。

**自动法：DEV_LAB_001 先行试点，过厂家验证清单再放产。** 试点前提全部就绪：锚点持久化 + 回灌（0031，已上）、`/recalibrate` 同帧锚点（已上）、重放台（`RawFrameReplay`，已适配 1.6）。试点流程按算法说明的五项验证：静态重复性 → 加载/卸载 → 温度影响 → 幅值裕量 → **断电恢复**（这项直接检验我们的回灌链路）。放产判据：连续两周 Δt 无周期级跳变、无效率 < 阈值法对照通道、重启前后连续。

试点期专属观测项（自动法特有的失败模式是"有数值的错"）：

- `measurements` 里同通道 Δt 出现 ≈T0 整数倍的阶跃 → 周期跳变，立刻停用回退阈值法；
- 状态码 −4（SimilarityLow）在 1.6 自动法里实际含义是"周期估计失败/找不到合格过零"（评估 §10 问题 #3），告警文案别按字面"相似度低"写。

**动态特征法：不入生产，允许诊断。** "包络形状改变会产生缓慢漂移，不一定立即报错"（指南 §4.5 原文）——安全监测里最怕的就是这种错法。仅在探头劣化诊断时作为第二意见（它对包络敏感恰好是探测包络变形的信号）。

### 2.3 每通道落位

`channels.meas_mode` 已是每通道配置，不需要新开发。规则：新通道建档默认 2；自动法通道必须经过"扫波 → 置零（锚点落库）→ 五项验证"流程才允许 `meas_mode=0`，直接改字段跳过置零的，SDK 会走无锚点分支重新捕获——这正是要防的漂移源头。

## 3. 连接拓扑：FxClient 保持，FxServer 备着

**现状匹配度**：现场是"串口服务器固定 IP，SDK 主动连"（`192.168.0.7:23` 这类），FxClient 是正确形态。我们的连接管理（会话锁、代次守卫、看门狗重连、多设备 DB 驱动）都建在这条链路上，运行稳定。

**FxServer 的真实价值**（指南 §7 精读结论）：设备端网络模块配成 TCP Client 主动连中心的场景——4G/NAT、无固定 IP、单端口多设备。它不是"更好的 FxClient"，是**另一种拓扑**，接入代价不小：

- 设备识别三策略各有坑：协议地址（默认，但**待机设备不发业务帧就识别不出来**，要做 Pending Session + 安全探测）；远端 IP（4G 下不稳）；监听端口（一口一设备，最可靠但费端口）；
- 生命周期反转：没有"重连"概念，只有"等设备回来"——看门狗语义、`FxConnectorState` 状态机、`IngestionService` 对账全要适配；
- 会话替换竞态：`ReplaceExistingDeviceSession=true` 时旧会话的断开事件不能把新会话标离线（指南 §7.5 点名）——和我们现有的会话代次守卫是同一类问题，方案可复用。

**触发条件**（满足其一再立项，预估 3~5 人日）：现场出现 4G/无线接入需求；或单中心接管 >10 台分散设备。接入形态：`FxServerConnector : IFxConnector` + `OnDeviceIdentified` 里按协议地址映射 `devices` 行 + 复用现有 Ingestion 管线。`devices.comm_type=2` 的语义留给它（入口校验现在拒 2，到时候放开）。

## 4. 温度设计：Direct 已定，剩下的都是个案手段

全局 `TempTauProfile.Direct` 本周已落（`FxConnectorFactory` 静态构造），理由在 plan §7 决策点 2。指南 §4.6 的完整菜单里还有两样备用：

- **通道级 `TempTauSeconds`**（优先于全局）：等 preflight 第 4 项查清现场上报间隔后，若某通道 PT1000 噪声可见且上报间隔 < 40s，可单通道给 60~180s——不动全局、不污染其他通道口径。用的时候 `channels` 表加列再说，别预建；
- **`UseTempChannel`**（借邻通道温度）：探头不带温度或温度探头坏的应急手段，现场出现该硬件组合再接。

**RawTemp 落库：暂缓。** Direct 档下 SpTemp ≈ RawTemp（只差超范围兜底），单独落列每行成本换不来信息量。哪天决定切 Balanced（届时必须做 `measurements` 语义标记列，plan §7 决策点 4 会翻案），RawTemp 一并落。

## 5. 信号质量监控补强（本文唯一建议新开发的项）

算法说明用了整整一章讲探头劣化："**有数值不代表粘贴正常**——自动法和动态特征法可能从残余回波中得到连续、看似合理的声时差"，并要求"轴力结果与信号质量分开监控，至少记录峰值、有效/无效状态、连续无效次数、波形质量变化"。

**我们已有的**：`signal_lost` 无回波超时告警（`SignalHealthService`，120s 无帧）、`measurement_anomalies` 表（负状态码全落）、`wave_features` 波形特征、probe-scan 通道自动检测。

**缺口正好是厂家点名的中间地带**——"有帧但在劣化"：

| 建议项 | 检测什么 | 实现落点 | 量级 |
|---|---|---|---|
| 连续无效帧告警 | 同通道连续 N 帧 StatusCode<0（探头松动早期：时好时坏） | `SignalHealthService` 加一条 anomalies 计数查询，产 `signal_degraded` 告警 | ~1 人日 |
| 峰值趋势预警 | "轴力平稳但峰值持续下降"（厂家判劣化的第一信号） | `wave_features` 已有峰值特征，加周期性趋势比对（周环比降幅阈值） | 1~2 人日 |
| 状态码 11/12 呈现 | 设备侧业务超限（有效值） | 不告警不丢弃（现有 `>=0` 落库逻辑已对）；前端测量列表加"设备超限"徽标即可 | 0.5 人日 |

这三项都不碰采集链路，纯消费侧，随时可做。优先级：连续无效帧 > 峰值趋势 > 徽标。

## 6. AGC：只进调试工位，不进自动化

1.6 的 AGC 是"从当前增益夹逼 + 二分搜索 + 饱和平台检测"，目标峰值默认体系也变了（SignalAuto 600→400）。指南 §6.6 的用法约束很清楚：AGC 是独占的通道控制会话，完成后要恢复原工作模式。

**用途**：通道验收/新装探头调参时替代人工试增益（probe-scan 之后、置零之前跑一轮，`targetPeak≈350`、`gainRange 1..47`）。**约束**：

- 固定阈值（`Threshold≠0`）通道跑完 AGC **必须重新置零**——增益变了幅值变，固定阈值在包络上的交越点可能跨周期（评估 §4.4）；相对阈值（=0）通道免疫；
- 1.6 里 `ConfigureChannelAsync` 改 Gain 会自动清包络追踪锚点，自动法通道 AGC 后同样要重新置零——SDK 帮你把"忘了重置零"这个坑变成了显式行为，算进步；
- 不进无人值守自动化：增益是标定基线的一部分，变更必须有人签发（现有 configure-channel 审批流的语义）。

**实现**：`DiagnosticEndpoints` 加一个 reviewer+ 权限的 `/agc` 端点（会话锁内跑、完成恢复 MultiMeas），要用再做，半天到一天。

## 7. 两处链路对齐检查（换源后遗留的设计确认）

### 7.1 启动时要不要把硬件参数写回设备

厂家推荐启动序列（指南 §2.4）：Standby → 会话上下文(sendCommand=false) → **逐通道硬件参数下发(sendCommand=true)** → MeasConfig → MCRConfig → MultiMeas。

我们的序列：会话上下文(false) + 对时 → Connected → MultiMeas → MCRConfig 收敛。**刻意不下发硬件参数**——设备自身存储是 ProbeFreq/Gain/EchoWin 的权威源，现场用厂家工具调机后我们不覆盖。

这是两种权威源模型的选择，不是谁对谁错：厂家模型"库是权威，每次启动灌设备"；我们模型"设备是权威，库是快照"。**保持我们的模型**（现场调机习惯依赖它），但补一个对账手段：`device_parameter_history` 已有参数回读链路，加一条定期"读回 vs 库配置"的 diff 告警（谁改了设备参数而库不知道，正是要暴露的事）。列入近期候选，与 §5 的补强同批。

### 7.2 看门狗判据与轮询模式的耦合

指南 §5.6 警告："不要仅因 60 秒无业务数据判定 TCP 断开——低频监测可能长时间无帧"。我们的看门狗 `NoDataTimeoutSeconds=60` 建立在**连续轮询**（`MCRConfig.DailyCount=0`）之上，现场也确实全是连续模式，不冲突。但 `DailyCount>0`（每日定时 N 轮）一旦启用，60s 判据必然误杀。在 `troubleshooting.md` 记一条：启用定时轮询前，看门狗超时改为 `max(轮询间隔×1.5, 60s)`——1.6 自己的 `ResolveReceiveActivityTimeout` 就是这个公式（`TcpSession.cs:462-480`），哪怕我们关了它的超时断线，公式值得抄。

## 8. 明确不采纳的清单（与理由）

| 能力 | 不采纳理由 |
|---|---|
| SDK `DeltaTof` 进预紧力链 | 预紧力必须走自家链（`EchoTime` 原始值 + 自算温补 + 标定系数），SDK 温补口径与我们不同且 RefTemp 缺失时静默用 22.22°C；`delta_tof_ns` 列继续只留痕 |
| `CalcUltraResult` 公式工具 | 我们有完整标定体系（最小二乘 + 不确定度 + 会签），字符串公式工具是给没有标定系统的集成商用的 |
| Model=5（28 通道高频版） | 无对应硬件；协议处理器已随源码入库，硬件到了直接可用 |
| 多终端 LoRa Mesh（逻辑通道） | 现场全部单终端直连（Address=1，逻辑通道=物理通道）。若上 LoRa 拓扑，`devices`/`channels` 建模要加终端地址维度（指南 §3.3 明确要求持久化 address+physical channel，我们已这么存，改动面可控） |
| DualMeas / TWaveRead 双波横波 | "按设备能力"（指南附录 B）——能力未证实。**价值高**（双波可免温补，直接消掉温度这个最大误差源），列入厂家求证清单：现场设备固件是否支持、精度指标、TEchoConfig 配置方法 |
| `FxUtility.MinTemp/MaxTemp` 调整 | 默认 −40~120°C 覆盖现场工况 |

## 9. 落地路线

**第一梯队（已完成，本周换源时顺手落地）**：锚点持久化全链路、温度 Direct、心跳 2s/关接收超时、状态码枚举适配、comm_type=2 三道防线。

**第二梯队（近期，合计 3~4 人日，纯消费侧不碰采集）**：

1. 连续无效帧告警 + 峰值趋势预警（§5，厂家强要求的缺口）
2. 设备参数对账 diff 告警（§7.1）
3. 前端 11/12 徽标（§5，顺手）

**第三梯队（条件触发）**：

| 项 | 触发条件 |
|---|---|
| 自动法生产放行 | 金样同源比对通过 + DEV_LAB_001 五项验证 + 连续两周试点达标 |
| AGC 调试端点 | 现场验收工位提出需求 |
| FxServer 接入 | 4G/NAT 设备或单中心 >10 台分散设备 |
| 双波测量 | 厂家确认设备能力与精度指标 |
| 通道级 TempTau / RawTemp 落库 | preflight 查清上报间隔后按个案；或决定切 Balanced 时 |
